The KV cache, and the
economics of inference

the table persists, only the probe is new

This door opens off section 11, where we noticed something alarming about the generation loop: producing token 1,001 apparently means re-processing tokens 1 through 1,000 from scratch. You'll want the attention equation from section 16 in your head — queries as search probes, keys as the table being searched, values as what gets retrieved — and the causal mask, because the entire trick behind this door is a consequence of masking. Nothing new is added to the machine here. We just stop throwing work away, and then follow the consequences all the way to the price list on your favorite model provider's website.

01The loop, honestly costed

The generation loop from section 11: run a forward pass over the sequence, get a distribution for the next token, sample one, append it, repeat. Written that way, each pass processes the whole sequence — and the sequence grows by one every step.

Count what that costs. Attention on n tokens builds an [n × n] score table, so a pass over n tokens does on the order of n² work in every attention block — and the projections that make Q, K, V and feed the MLPs do a matmul for every one of the n positions. To generate a 1,000-token reply this way, you'd run a full pass at length 1,001, then 1,002, then 1,003… The position-wise work alone, summed over the loop, grows with the square of the reply length; the attention tables push it toward a cube. All to produce one token per pass, at the last position, while recomputing the other thousand positions to results we could have predicted perfectly — because we already computed them last step.

That last clause is the whole door. Why are the old results identical from step to step?

02What never changes

Because of the causal mask. Position i is forbidden from consulting anything after i — that was the point of adding −∞ above the diagonal in section 16. So everything the model computes at position i, in every layer, depends only on tokens 1 through i. Appending token n+1 to the sequence changes nothing upstream of it: token 42's residual stream, its keys, its values are bit-for-bit what they were before the new token existed. The past is sealed by construction.

Look at what one generation step actually adds to the attention picture:

        keys →   t1   t2   t3   t4  │ t5
  queries                           │
  ↓  t1          ■    −∞   −∞   −∞  │ −∞
     t2          ■    ■    −∞   −∞  │ −∞        old rows: already
     t3          ■    ■    ■    −∞  │ −∞        computed last step,
     t4          ■    ■    ■    ■   │ −∞        unchanged forever
   ─────────────────────────────────┼──────
     t5          □    □    □    □   │ □    ← the only new row
One step of generation grows the causal score table by one row (t5's search over
everything) and one column (t5's key, which no earlier query is allowed to see).

The new column is all −∞: earlier positions may not look at t5, so their attention rows — and therefore their outputs, and therefore everything downstream — are untouched. The only new work in the entire [n × n] table is the bottom row: one new query, searched against all the old keys. And note which letters that row needs. It needs t5's own q, k, and v, freshly computed. From the past it needs only the keys and the values — the table being searched and the content to retrieve. The old queries are never needed again: a probe is used the moment it's made, and discarded. That asymmetry names the cache.

03Generation as an append

So: in every layer, keep the keys and values of every token processed so far — two growing lists per attention head, called the KV cache. A generation step becomes:

for each layer:
    q, k, v  ←  project the ONE new token          (three small matmuls)
    append k, v to this layer's cache               (the table grows by one entry)
    scores   ←  q · every key in the cache          (one row of dot products)
    output   ←  softmax(scores) · cached values     (one weighted blend)
    … MLP on the one new token, as usual …
Per step, per layer: project one token, search one probe over the accumulated
table, retrieve one blend. Nothing is recomputed; the past is read, not re-derived.

Every operation is one of our familiar friends — the same dot-product search as always, just performed by a single fresh probe over a table that persists between steps. The forward pass over n tokens has become a forward pass over one token that consults n entries of stored table. Per-step cost drops from "re-run everything" to "project one token and take one row of dot products": linear in the past instead of quadratic, and the summed cost of a whole reply drops by a factor of roughly the reply length. Generating token 1,001 does about a thousandth of the naive work.

Two honesty notes. First, the cache is not an approximation — it computes mathematically identical outputs to the naive recomputation (only the floating-point rounding order differs). It's pure bookkeeping, the same trick as remembering a running total instead of re-adding the column of figures each time. Second, the cache is only possible because the mask is causal. A bidirectional model like BERT lets every position see every other, so appending a token would genuinely change all the old representations — nothing could be cached. The causal mask looked like a restriction back in section 16; it's also a gift.

04The bill arrives in bytes

Nothing is free. We bought speed by storing the past instead of recomputing it, so the cost moved from arithmetic to memory — and it's worth doing the arithmetic on the memory, because the numbers come out shockingly large.

Each cached entry is two vectors (a key and a value) per attention head, per layer. Take a respectable open model of the 7B class — 32 layers, 32 heads of 128 dimensions each — storing its cache at 2 bytes per number:

per token:   2 vectors · 32 layers · 32 heads · 128 dims · 2 bytes
           = 524,288 bytes                          ≈ ½ MB per token

per sequence at a 4,096-token context:              ≈ 2 GB
serving 16 users at once:                           ≈ 32 GB

… which no longer fits beside the model's own 14 GB of weights
on a 40 GB GPU.
The KV cache ledger. Half a megabyte per token sounds like nothing; multiplied
by context length and batch size it out-eats the model itself.

This is the central budget of serving language models. The weights are a fixed cost, paid once per GPU; the cache grows with every token of every concurrent conversation. Long contexts and big batches — the two things everybody wants — are both purchases of exactly this currency. When a provider limits your context window, or when a local model slows to a crawl as the chat grows, you are usually watching this table strain against a memory ceiling.

05Shrinking the table: MQA, GQA, and kin

The pressure of that ledger has reshaped the architecture itself. Look at where the bytes went: 32 heads each keeping a private K and V table. But recall from section 15 what the heads are for — running searches in parallel from different perspectives. The searches need to differ; must each search also keep its own private copy of the library?

Multi-query attention (MQA) answers with a hard no: keep 32 distinct query heads but share one single K and V table among them all — a 32× smaller cache, at some cost in quality, since every probe now searches the same index of the past. Grouped-query attention (GQA) is the compromise that stuck: small groups of query heads share a KV table. Eight KV heads serving 32 query heads is a typical arrangement — a 4× smaller cache, nearly indistinguishable quality — and some form of head-sharing is in essentially every major model trained since about 2023. When the main essay's door sign said the cache's footprint is "what GQA exists to shrink," this is the shrinking.

The squeezing continues past head-sharing, and one honesty note covers the lot: sliding-window attention caps how far back some layers may look, so their cache stops growing at the window size; quantizing the cache to fewer bytes per number is routine; and the latent-attention family (DeepSeek's MLA and kin) stores only a small compressed latent per token in place of full keys and values, arranging the attention arithmetic to run against the latents directly — a little more math, the cheap currency, for a lot less memory, the expensive one. Different mechanisms, one motive: everyone is paying rent on the same table.

06The two phases, and the price list

The cache also splits inference into two visibly different phases, and the split explains some things you have personally experienced.

Prefill: the prompt arrives all at once, so the model processes it the way it was trained — every position in parallel, one big pass, the full triangular score table, all of it riding the bullet train of engineering reality #1 from section 08. Prefill's job is to fill the cache and produce the first new token. It is compute-bound: the GPU's multipliers are the bottleneck, and they are legion.

Decode: then the loop begins, one token at a time, each step a single probe against the whole cache. The arithmetic per step is modest; the problem is that the step must read the entire cache — and every one of the model's weights — from memory: gigabytes of traffic to do a few billion multiplications, roughly one multiply per byte fetched when the hardware wants hundreds. Decode is memory-bandwidth-bound: the multipliers idle while bytes crawl in from VRAM. It's also serial by construction — token 1,002 depends on token 1,001 — though tricks like speculative decoding claw some wall-clock parallelism back.

Now read a model provider's price list: input tokens several times cheaper than output tokens. That ratio is this door. Input tokens are prefill — parallel, efficient, amortized; output tokens are decode — serial steps, each dragging the weights and the full cache past the compute units, each occupying scarce cache memory for the duration. The same split shows up in the feel of a chat: the pause before the first word is prefill, the steady drip thereafter is decode. Two different machines, in effect, running the same weights.

And that is the economics of inference in one sentence: generation is a search over a table you must keep, and you pay for arithmetic during prefill but for memory ever after.
