FlashAttention:
the same math, faster

never write down the thing you're about to throw away

This door opens off section 16, where the full [n × n] attention table appeared, and it leans hard on engineering reality #1 from section 08 — computers are shockingly good at matrix multiplication. Behind this door we discover the fine print on that sentence: they are shockingly good at the multiplying, and comparatively terrible at fetching the numbers to multiply. FlashAttention is not a new kind of attention. It computes exactly the equation you already own, to the last bit of intent, and gets its speed purely by refusing to write a large intermediate result into slow memory. It's the sibling of door 01: another story about arithmetic being cheap and bytes being expensive, this time during training and prefill rather than decode.

01Where the time actually goes

A modern GPU is two machines in an awkward marriage. One is an arithmetic engine that can perform hundreds of trillions of multiply-adds per second. The other is a memory system — called HBM, high-bandwidth memory, the gigabytes quoted on the spec sheet — that, despite the flattering name, can only deliver a few trillion bytes per second. Divide the two numbers: to keep the arithmetic engine busy, every byte fetched from memory must be used in dozens to hundreds of operations. An operation that does lots of math per byte (a big matrix multiplication, conveniently) runs at full speed and is compute-bound. An operation that does one or two operations per byte — reading a huge array just to exponentiate it, say — leaves the multipliers idle, waiting on deliveries. It is memory-bound, and the spec-sheet teraflops are a fantasy for it.

There is also a third character: a few dozen megabytes of on-chip memory (SRAM), sitting right beside the arithmetic units, an order of magnitude faster than HBM — and tiny, and carved into slices of a couple hundred kilobytes, one per compute cluster, which is what a working tile must actually fit inside. Everything in this door is about choreographing work so that the bulky intermediate results live and die in that small fast room, and the slow big room is visited as rarely as possible.

02Attention, as naively served

Write the attention equation the way a straightforward implementation executes it, and count the trips to slow memory. For a 4,096-token sequence, the score table has 4,096 × 4,096 ≈ 16.8 million entries — per head, per layer — which is far too big for the small fast room, so each intermediate goes out to HBM:

S = QKᵀ/√d      big matmul       → write 16.8M scores out to HBM
P = softmax(S)   read them back, exponentiate, normalize
                                  → write 16.8M weights out to HBM
out = PV         read them back  → the [n × d] table of blends, at last
Two full round trips of an [n × n] object through slow memory, to produce an
[n × d] result. The matmuls fly; the score table commutes.

The matmuls at either end are compute-bound and genuinely fast. The middle is the problem: softmax does a handful of operations per entry, so those two round trips run at memory speed. Worse, the traffic grows with n² while the useful output grows with n — quadruple the context and the wasted commuting grows sixteen-fold. And the object we're shipping back and forth is pure scaffolding: nobody wants the score table itself, only the little [n × d] blend it produces. We are paying premium freight to warehouse something we're about to discard.

The obvious fix: compute the table in small tiles that fit in the fast room, use each tile immediately, and never ship it out at all. One obstacle stands in the way, and it's the softmax.

03The obstacle: softmax is a whole-row affair

Recall from section 14 how softmax is actually computed. For numerical safety you first subtract the row's maximum (so the exponentials can't overflow), then exponentiate, then divide by the sum:

softmax(x)i = exi − m / ℓ ,    m = max(x),   ℓ = Σj exj − m

Both m and ℓ are properties of the entire row — every score of one query's search over every key. Process the row in tiles and you seem stuck: the first tile can't be exponentiated correctly because a later tile might contain a bigger maximum, and nothing can be divided by ℓ until the whole row has been seen. It looks like softmax simply demands the full row be materialized somewhere. This is exactly the kind of obstacle that deserves suspicion — it has the same shape as "generation must re-read the whole past" from door 01, and it falls to the same weapon: keep a little running bookkeeping, and correct as you go.

04Online softmax: bookkeeping to the rescue

Walk the row one tile at a time, carrying three running quantities: the biggest score seen so far (m), the sum of exponentials so far (ℓ), and — we'll need it in a moment — the weighted blend of values so far. When a new tile arrives containing a new maximum, every exponential already banked was computed against the old, too-small m. But look at what the error is: each banked term is ex−mold when it should be ex−mnew, so every term is off by the same factor, emold−mnew. One multiplication rescales the entire past. Watch it work on a row revealed two scores at a time:

the row, in tiles:      [ 2   1 ] [ 3   0 ]

tile 1:   m = 2,  ℓ = e⁰ + e⁻¹                    = 1.368
tile 2:   new max 3 — the banked ℓ is stale by e^(2−3)
          ℓ = 1.368·e⁻¹ + (e⁰ + e⁻³)  = 0.503 + 1.050  = 1.553

answer key (whole row at once, m = 3):
          ℓ = e⁻¹ + e⁻² + e⁰ + e⁻³                 = 1.553  ✓
The running sum, corrected on the fly. No tile ever needed to see another
tile; the same rescaling fixes the running blend of values.

The value blend obeys the same rule: it's a sum of ex−m-weighted value vectors, so a change of m rescales the accumulated blend by the identical factor, and the final division by ℓ happens once, at the end of the row. This trick — online softmax — computes exactly the textbook softmax, not an approximation of it, while touching each score exactly once. Like the KV cache, it's pure bookkeeping: the running-total trick, again, wearing a numerically-stable coat.

05The tiled dance

Now the whole algorithm assembles itself. Load a block of queries into the fast room. Stream blocks of keys and values through it. For each incoming block: compute the score tile (a small matmul, compute-bound, happy), fold it into the running m, ℓ, and blend by online softmax, and let the tile evaporate — it never existed outside the fast room. When the last block has streamed past, divide by ℓ and write the finished [block × d] output to slow memory, once.

          K,V blocks →  ▓▓ → ▓▓ → ▓▓ → ▓▓
                         │
  Q block, resident  ┌───▼──────────────────┐
  in the fast room → │ score tile · m, ℓ,   │ → output written
                     │ running blend        │   to HBM once
                     └──────────────────────┘
        the [n × n] table, never materialized
Each score tile is born, used, and discarded on-chip. Slow memory sees only
Q, K, V on the way in and the finished output on the way out.

Slow-memory traffic drops from "round trips of n²" to "read the inputs, write the answer" — the scaffolding is gone from the freight bill. In practice that's a wall-clock speedup of roughly two to four times on real workloads, and — often more important — the memory needed for attention drops from quadratic in sequence length to linear, since the table is never stored. Training on long sequences went from "cannot fit" to "fine" the day this shipped, which is much of why it's simply the default in every serious framework now. (A historical footnote for the careful: the 2022 original streamed query blocks past resident K/V; FlashAttention-2 flipped the loop to the queries-resident version shown here, and -3 retuned the dance for newer hardware. The choreography improves, the math never changes.)

06What it is, and isn't

One loose end: training. Backpropagation — engineering reality #2 — needs the attention weights to compute gradients, and we conspicuously refused to keep them. The fix is a deliberate trade in the now-familiar currency exchange: save only each row's tiny softmax statistics (m and ℓ), and during the backward pass recompute the score tiles on-chip from Q and K. More arithmetic — the cheap thing — in exchange for never storing n² values, the expensive thing. Sound familiar? It's the same exchange rate quoted behind door 01, and paying arithmetic to avoid bytes is the closest thing this corridor has to a running theme.

The honesty notes, which for this door are really its moral. First: FlashAttention is exact. It is not sparse attention, not an approximation, not a new architecture — every honesty note from section 16 still applies because it is section 16, rescheduled. Second: the quadratic arithmetic is all still there; only the quadratic memory traffic is gone. The n² wall was pushed back, not torn down, and behind the next door down the corridor live both the tricks that genuinely soften the quadratic — sliding windows and their kin — and the RoPE surgery that stretches how far a model can see at all; that door is now open. Third, and most general: "efficient" is not a property of an algorithm. It's a property of an algorithm on a machine. The math of attention didn't change in 2022; somebody finally read the machine's freight tariff closely. It's engineering reality #1 with its second clause restored: computers are shockingly good at matrix multiplication — provided you keep the matrices where the multipliers can reach them.
